# #191 stack A/B: mlx-serve against ds4

Draft. The run is complete: 8 sweeps, 120 rows. Every figure comes from the
report output at `~/bench-logs/191-head-selector/191-mlx-ab-report.txt`,
generated by the patched report at HEAD eb5a2bb. The wall-tail turn counts in
the post-hoc section come from the ledger, because the report does not emit
turn counts; every other figure is traceable to a line in the report.

## What this is

A SCREEN, not a superiority test. Both endpoints pair by task, so each has
fifteen pairs, not sixty rows. The observed CI is the honest statement of
precision. It answers one question: does the new stack integrate and regress
nothing catastrophically? It does not rank the two stacks.

## The confound, stated once

mlx-serve runs a different engine, a different weight format, and a different
decoding path than ds4. Engine, quant, and speculative decoding move
together; none can be attributed alone. This is a stack comparison, and it is
reported as one. Any sentence that names one arm names the whole stack, not a
component.

The decoding difference, plainly: mlx-serve speculates via prompt-lookup
decoding (n-gram, draft_len=5, self-gating on ngram score), on by default in
mlx-serve 26.9.1 and active throughout the run. ds4 runs without a draft path
in this configuration — no MTP sidecar is passed. This is stack-as-shipped,
which is what #191 pre-registered; it does not void the run. The requirement
is to name it, and to never attribute a wall-time difference to "the engine"
when a draft path is one of the things that differs.

## The shim asymmetry

The two arms run different paths, by design. ds4 runs behind `qwen_tool_shim`
on :8101 with strip ON; mlx-serve runs bare on :11234. That difference is the
asymmetry, not its absence.

The shim exists to correct a tool-call pathology that is ds4's, not the
model's. Step 0 probed whether mlx-serve exhibits the same pathology. It does
not — ABSENT. So shimming ds4 while running mlx bare does not hand ds4 an
advantage the other arm is denied; it compensates for a defect the other arm
does not have. Had the probe gone the other way, a bare mlx arm against a
shimmed ds4 arm would have handed ds4 roughly 23 points, and the run would
have been void as designed.

## Method

- Paired by task throughout. Pass rate by sign test on discordant tasks.
- Wall time as the mean of per-task log ratios on tasks both arms PASSED.
- Rows selected on `env.harness_head == 7932a5f` and `harness_dirty == false`;
  the timestamp cut is a cross-check that must agree. A disagreement voids
  the run.
- Each sweep owns [start, its own recorded finish]; a row between windows or
  after the last finish fits no window and is not counted.

The numbers were produced by the patched report at HEAD eb5a2bb. The run
itself was measured under the old selection; the patched report re-selected it
on the pinned head.

## Results

- Pass: new 59/60 / old 60/60 (sign test p=1.000)
- Wall: n_pairs 15, ratio 0.68 (95% CI 0.54-0.87), median 0.58
- Deaths: new 0 / old 0
- Verdict: SCREEN PASS

**The pass endpoint says nothing.** 1 down, 0 up, 14 tied of 15, p=1.000. One
discordant pair cannot discriminate; the test could not tell the arms apart,
not that they are equal. This task set saturates at the top (#79): both arms
cleared it almost completely, so the pass side of this screen was never going
to inform anything. That is worth knowing before anyone designs the 3+3.

**The wall endpoint pairs by task, so n_pairs is 15, not 60.** The
pre-registered resolution (~17-26% paired wall) was computed for n=60 and does
not describe this test. The observed CI, 0.54-0.87, is the honest statement
of precision here.

**The wall statistic is a geometric mean, and it compresses the tail.** The
pre-registered endpoint is the mean of per-task log ratios, which is a
geometric mean of wall times. It is the right answer to the registered
question and a misleading answer to "how long might this take me." On
`parser-mbox-quoting` the four mlx trials ran 39.4, 40.4, 283.2, and 1377.4
seconds; the four ds4 trials ran 45.0, 50.1, 53.9, and 66.4. The geometric
means are 157.9 vs 53.3 (a 2.96x gap); the arithmetic means are 435.1 vs 53.9
(an 8.1x gap). The geometric mean compresses the tail by a factor of about
2.7. The person waiting on that task waited 23 minutes, not 158 seconds.

**The server_argv warnings are expected for this run.** Every task on both
arms reports "none records server_argv; cannot verify they ran one
configuration." The field was added in patch 1, after these rows were
written. The check cannot pass for this run and will pass for the next one.
The claim is supported by other evidence: the harness was pinned at 7932a5f
for all eight sweeps, run-record.txt carries the effective server command
line for both arms, and the server was restarted once per sweep from a single
code path.

## The wall tail (post-hoc, exploratory)

Labelled post-hoc and exploratory in those words. Nothing here carries a
test, p-value, or CI, because every figure was chosen after seeing the data.

The mlx arm is bimodal in turns; ds4 is not. Across every pinned row ds4's
maximum is 20 turns; the mlx arm has produced 334 turns and wall times from
14.9s to 1377.4s on the same task, same server, same harness. All of those
rows PASSED — this is a wall-time tail, not a pass-rate effect.

The pre-registered endpoint — the mean of per-task log ratios on tasks both
arms passed — is reported as registered, unchanged. The tail is reported
separately, descriptively: per-task max turns and max wall per arm, the count
of rows above a stated turn threshold, and the full per-task spread rather
than a summary statistic.

Two tasks show single excursions far outside their own distribution:
`parser-mbox-quoting` ran 334 turns against its own 9, 9, and 35, and
`mbox-quoting-both-halves` ran 162. Both are wall-time tails, not pass-rate
effects; all of those rows passed.

Separately, `swift-downsample-buckets` runs 22-29 turns on mlx as its normal
behaviour (three of its four trials), against ds4's 11-14. That is a shift —
the task consistently costs more turns on the mlx stack — and it is a
different finding from a bimodal excursion. `swift-csv-text`'s 37 is a smaller
single excursion against its own 9, 14, and 17.

No sentence here says "mlx is faster." It is faster on most tasks in this
sample and catastrophically slower on a few, and the confounds — engine,
quant, prompt-lookup decoding — mean no component can be credited.

Sampling limit, stated plainly: at eight sweeps we have four observations per
task per arm. Four is thin for characterizing a tail, and the tail may exist
on ds4 unsampled. This write-up says that rather than let a reader infer ds4
is immune.

This is the #210 failure mode: a bimodal treatment averaged into a single
number. It cost us once already.

## What the screen says

SCREEN PASS: the new stack integrates and regresses nothing catastrophically;
book the paired 3+3 for a superiority claim.

## Open items

- The harness prints "no draft counters this trial (ds4-mtp-timing)" on every
  mlx trial. On the mlx arm that warning is misleading: the engine IS entering
  a speculative path, just not ds4's MTP path, which is what the counter
  measures. The counter is engine-specific and the warning's wording invites
  the opposite conclusion. File as its own issue after the run; do not fix
  the harness during the run.

- PLD hypothesis (untested): PLD is the mlx arm's draft path and it self-gates
  on n-gram score. A long tool-call loop is where recent context stops
  resembling the prompt, so the gate flips and the speculative path stops
  helping. Whether the tail is caused by PLD or merely correlated with the
  same long sessions, this run cannot say — the two arms differ by three
  things at once. Experiment that would test it: same engine, PLD on versus
  off, one variable.

- CI checks pytest and ruff format only. It does not run ruff check or mypy:
  ruff check has 70 errors (mostly pre-existing debt in files these patches
  never touch) and mypy has no [tool.mypy] section in pyproject.toml. Neither
  is a gate today, which is #218's complaint almost word for word: green on
  things it never checks. File as its own issue after the run; do not expand
  this change to fix them.
