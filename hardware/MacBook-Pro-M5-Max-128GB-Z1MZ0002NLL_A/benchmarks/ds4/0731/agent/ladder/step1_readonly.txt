`ds4_kvstore.c` implements a durable, on-disk KV-cache/checkpoint store for the ds4 LLM inference engine. Here's what it does:

- **Persistent prompt/KV checkpoints on disk.** It snapshots the live token prefix (KV cache state) into files keyed by a SHA-1 hash of the rendered prompt text, so a later conversation starting with the same text bytes can reload the graph state and skip cold prefill. Files are named `<sha1>.kv` with a fixed binary header (magic `KVC`, version, payload ABI, model id, quant bits, reason, token/hit counts, ctx size, timestamps).

- **Budgeted eviction policy.** A `budget_bytes` cap (default `DS4_KVSTORE_DEFAULT_MB`) keeps total on-disk footprint bounded. `ds4_kvstore_evict()` scores each checkpoint (`ds4_kvstore_entry_eviction_score`) by hit-count (decayed by a half-life), token density (`tokens/file_size`), and anchor/reason priors, then unlinks the lowest-scoring files until the budget fits. It also special-cases evicting a *continued* checkpoint that is a strict prefix of the incoming store.

- **Store path with staged atomic writes.** `ds4_kvstore_store_live_prefix_text()` renders the token prefix to text, hashes it, checks for a compatible existing file (model/quant/ctx constraints via `kv_cache_existing_compatible`), stages the session's KV payload, verifies the projected file fits the budget, writes to a `*.tmp.<pid>` file, renames into place, and only records a hit. A `cache_text_override`/`ext_flags` path lets callers store non-token-text keys (e.g. "visible-transcript"), and optional `trailer_hooks` attach protocol-specific extras (like the server's tool-id → DSML trailer).

- **Load path with text-prefix matching.** `ds4_kvstore_try_load_text()` finds the longest compatible prefix whose SHA matches the prompt bytes, validates header/hash/prefix, loads the stored payload into the session, and rebuilds the effective prompt from the exact stored token history plus a tokenized text suffix (handles tokenizer boundary merges). On hit it bumps the file's hit count (`touch_file`) and reports timing/quant/key metadata via `ds4_kvstore_load_result`.

- **Shared low-level format used by both ds4-server and ds4-agent.** The header comment notes the file layout/payload helpers are intentionally shared; ds4-server owns the automatic byte-prefix cache policy on top, while ds4-agent uses the same durable format for explicit sessions with its own policy. It includes a self-contained SHA-1 implementation, little-endian serialization helpers, monotonic-clock timing, and a logging callback (`kv_logf`) for cache hit/evict/store telemetry.
