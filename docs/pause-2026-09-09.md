### CI went red during this sweep, and the cause is worth knowing

Three commits ran red before it was caught. `NEXT.md` is generated from issue
bodies verbatim, and #264 -- an issue *about* a driver that was retired to
`vault/` -- carries that driver's old `scripts/` path in its body. When #264
entered the top of the queue, the path came with it, and
`tests/test_vault.py` failed: nothing live may hand a reader a runnable path
to an archived shell.

Fixed in `make_next.py`, which now strips the `scripts/` prefix from any
shell that lives in `vault/` while keeping its name, since a summary about a
shell that cannot name the shell says nothing. The vault list is read from
disk, so retiring the next driver needs no edit here.

The general shape, which will recur: **a generated file inherits the
constraints of everything it quotes.** `make_next.py` had no idea a guard
existed; the guard had no idea a generator would feed it.

## #279 was the blocker. It is not the blocker it says it is.

The opening post claims the engine never accepted the hyphenated `qwen4-exp`
spelling, so the pack is at fault. **That is wrong**, and it was corrected on
the issue at the pause. The evidence for it was
`git log -S'"qwen4-exp"' -- ds4.c` returning nothing — a false negative,
because the literal in the source is `"qwen4-exp.block_count"`, never the bare
string.

What the trees actually say, cited with shas because several ds4 trees exist
and this file moves daily:

| | `ba01f5d` (where we sit) | `6c1e836` (the reverted move) |
|---|---|---|
| the arch macro | `ba01f5d:ds4_qwen4.h:8` = `"qwen4-exp"` | `6c1e836:ds4_qwen4.h:8`, unchanged |
| dispatch | `ba01f5d:ds4.c:6419` via the macro | `6c1e836:ds4.c:6803` via the literal `"qwen4exp"` |
| `qwen4-exp.` metadata keys | present | none |

One site moved to a bare literal and the header did not follow, in `b020c9f`
"Integrate Qwen3.8 qwen4exp inference and conversion tooling".

**Upstream ships the migration.**
`6c1e836:gguf-tools/qwen4_pack_to_qwen4exp.py` converts a fast-pack into the
single-file `qwen4exp` schema — merging the base GGUF with the external Q4_1
PLE sidecar, renaming tensors to the llama.cpp schema, converting BF16
control tensors to F32, computing `ssm_a = -exp(A_log)`, splitting the fused
indexer qk projection, permuting GDN per-head vectors, and inlining the
dequantized PLE table. It is a schema conversion, not a metadata edit, so
"rewrite the GGUF string" was never an option.

**The path on return:** run the converter against the `-q4` pack and its PLE
sidecar, repoint the six drivers, and parity-check the output before
publishing any number from it. #228 is not blocked the way #279 claimed.

## What shipped last

**#276 — do maximum fans make the GPU faster?** Answered and closed.
Maximum fans hold the die **8.48 C** cooler and buy **0.6% decode**, which is
reconciled by **+0.78% SoC power**: the cooling is real and it buys almost
nothing, because this chip was not thermally limited to begin with. On auto,
peak die hit 99.61 / 99.39 / 99.41 C across the three segments. A +1.8%
prefill reading was discounted — the pairs trend 4.4% -> 1.8% -> 0.9%, which
is a first-phase artifact, not an effect.

Secondary result, and the more useful one operationally: cooling on maximum
fans saves roughly **45 minutes per six-phase A/B** and reaches a
die-to-ambient delta of 5.2 C against 10-11 C on auto.

All raw data is in `benchmarks/ds4/fan-ab-276/` — 144 rows x 49 columns with
no blanks, per-second sensors, 18 raw CSVs, the manifest and the run log. It
was kept complete deliberately, for a possible write-up.

The method that came out of it is in `docs/m5max-runbook.md` under "Thermal
tests: what a fan or cooling comparison must do". The finding worth carrying
to any other project: **a threshold on a difference is a rate limit nobody
wrote down.** The original settle gate accepted 0.3 C between consecutive 30 s
medians, which restates as **36 C/hour**. It was replaced with a least-squares
slope over a trailing window, bounded at 0.3 C/min — calibrated against a
settled die's own noise (p90 0.277 C/min, n=820), not guessed.
