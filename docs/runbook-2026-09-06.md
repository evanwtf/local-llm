## 0. Confirm the batch actually completed

    tail -3 <batch log>
    cat benchmarks/agent/results-146-targets-ab-manifest.jsonl

A manifest row with `"arm":"VOID"` means the batch voided itself on the cutoff
and there is no result. 60 rows expected: 15 tasks x 4 runs, arms `legacy
sandbox sandbox legacy`.

**The manifest mixes batches.** `results-146-targets-ab-manifest.jsonl` already
held 2 rows from an earlier run at 09:21 before this batch appended to it, so
"4 manifest rows" is not a completion test and the last 4 rows are the ones
that belong to this batch. The same is true of the results file: it held 30
rows from earlier batches, so the readout must select this batch's rows before
counting anything. Quoting the file's total row count as batch progress is a
mistake already made once today.

**Use a full ISO8601 boundary and compare parsed datetimes, not strings.**

    from datetime import datetime
    START = datetime.fromisoformat("2026-09-06T17:16:00")
    cur = [r for r in rows if datetime.fromisoformat(r["started"]) >= START]

The first row of this batch is `2026-09-06T17:16:48`; the last row of the
previous one is `2026-09-06T09:19:50`. A truncated `started >= "...T17:16"`
compares strings, which happens to work only because every `started` in this
file is exactly 19 characters with no `Z`, no offset and no sub-second part. A
row written in any other shape sorts unpredictably against a truncated bound,
and the failure is silent -- rows quietly join or leave the batch. Parsing
raises instead.

**This is a workaround, not the fix.** `targets_ab.sh:72` already computes a
batch id (`BATCH`, `0906-1716` here) and spends it only on the log directory
name at `:129`. It never reaches the rows, so every readout is forced to
guess the batch from wall-clock time. See the issue filed for this.
